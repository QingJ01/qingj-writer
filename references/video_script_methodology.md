# 视频脚本方法论（模式E/F细则）

这份文件是模式E（B站中视频脚本）和模式F（公众号文章改视频脚本）的细则。SKILL.md 里写的是规则，这里放理由、格式样板和改写对照。

情酱的价值观、材料关、信息保真、现实核验和绝对禁区在视频里全部照用。下面只写视频多出来的那部分。

## 来源

参考了 sugarforever/01coder-agent-skills 的 video-planner（MIT）、chenyuxiaojin/video-agent-skills（MIT）、ShortVideo-AI/short-video-script-skill（没有 LICENSE，只吸收思路），以及四位定位相近的B站技术口播账号公开作品，飞天闪客、马克的技术工作坊、轩辕的编程宇宙、浙大猫学长。吸收的是做法，文字按情酱的规则重写，人设、口头禅、固定尾部和亲身经历都不搬。跟情酱禁区冲突的写法见第九节。

## 一、听和读的差别

**观众不能回翻。** 读者没看懂可以往回扫一眼，观众只能接着往下听。所以视频比文章更怕长定语、嵌套从句和一句话塞四个信息点。主语和动作要更早出来，这一点跟情酱的中文词序规则方向一致，视频里只是更严。

**观众会走神，需要被拉回来。** 情酱长文里的扣主线句在视频里从节奏技巧变成必需品。每换一段，用一句话交代"我们现在在聊哪件事"。它仍然要是一句人话（"回到刚才那个报错"），不能是"接下来让我们进入第二部分"。

**一半的信息交给画面。** 数字、名字、命令、原文放到屏幕上，嘴上说它让你怎么想。嘴和屏念同一串数字，等于说了两遍，观众会走神。

**前30秒决定留不留。** 观众是被标题和封面点进来的，带着一个具体期待。开头先让他看到那个期待的影子，铺垫往后放。

**照着念出来才算写完。** 脚本是作者照着念的，不是给人读的。写完默念一遍，念到一半要回头看才懂的句子就是太书面。收的是书面腔，不是信息量，带判断带细节的句子留下。

## 二、照着念友好

**要改的**

- 长定语套长定语，"这个由三个人在两周里用业余时间做出来的开源项目"
- 一句话塞三四个信息点
- 被动腔和书面连接词，此外、基于上述、由此可见、与此同时
- 括号里的补充，念的时候没有括号
- 符号，→、≈、/、&、×，嘴上念不出来
- 阅读指代，如下图、上文提到、文末、往下翻、点击阅读原文
- 时长承诺，"今天五分钟讲清楚"。节奏让观众自己感受

**改成**

- 一句话一个意思，长链拆成两三句
- 主动句，先说谁做了什么
- 数据单独成句，同时上屏
- 英文名、版本号、缩写不好念的，第一次出现时在旁边标读法，`<!-- 读作 ... -->`
- 人名、书名、产品名说全称，剪辑才知道放谁的照片、哪本书的封面

**单句没有硬上限。** 情酱的句子本来就时长时短，视频里也不必把每句压到二十个字。判断标准只有一个，能不能一口气顺当念出来。长句中间有自然换气的逗号就行。

**一句话独立成段，在口播里就是一次停顿。** 真需要观众停一下的地方才这样写，连续五六个短句段排队喊结论，念出来像在打快板。

### 改写对照

下面是格式示范，花括号是占位，不是可以照抄的事实。

> **文章**　这个功能（目前只对付费用户开放）非常好用
> **口播**　这个功能我用下来挺顺手的。不过要说一句，现在只有付费用户能用

> **文章**　延迟从 1.2s 降到 0.4s，降幅约 67%
> **口播**　原来点一下要等一秒二，现在零点四秒。等的时间少了三分之二
> 【屏幕】数据卡，1.2s 和 0.4s 两根柱子

口播里的"少了三分之二"和原文的"降幅约67%"是同一个关系。不能顺嘴说成"快了67%"，延迟少了多少和速度快了多少是两种算法，关系保真在视频里同样要守。

> **文章**　如下图所示，{产品名}的设置页分成三栏
> **口播**　你看画面上这个设置页，它分成三栏
> 【屏幕】录屏，打开{产品名}设置页，鼠标依次划过三栏

> **文章**　这个由三个人在两周里用业余时间做出来的开源项目，已经有了{数字}个 star
> **口播**　这个开源项目，是三个人用业余时间做的，前后就两周。现在已经有{数字}个 star 了

> **文章**　上文提到的那个报错，在 v2.1 之后就消失了
> **口播**　刚才那个报错还记得吗。升到二点一版以后，它就没再出现过
> `<!-- 待核 录前确认 v2.1 这个版本号 -->`

## 三、屏上呈现

口播稿不只写说什么，还要告诉作者屏幕上放什么。逐段判断这段配什么画面最有说服力，判断"这段不需要画面"也是写稿人的工作。

### 脚本开头的总则

先列本期画面来源，再给一张段落到主画面的映射表，正文每段再落到具体内容。

```
## 屏上呈现总则

画面来源
- A 录屏，{产品名}官网和操作界面
- B 文字卡，数据卡、原文引用卡、对比卡
- C 真人出镜，开头和收尾

| 段落 | 主画面 | 具体放什么 |
|---|---|---|
| 开头 | C | 出镜，背景放{产品名}首页 |
| 先看它到底做了什么 | A | 官网首页从功能区慢滚 |
| 我踩到的第一个坑 | A和B | 报错截图，再叠一张原因卡 |
| 收尾 | C | 出镜 |
```

表格的表头、分隔行和每一行列数必须一致。内容太长放不进格子，就改成列表。

### 正文里的备注

| 标记 | 用途 | 写法 |
|---|---|---|
| 【屏幕】 | 这段或这一句放什么画面 | 【屏幕】终端里跑安装命令的输出 |
| 【纯口播】 | 这段不需要额外画面 | 单独一行 |
| 【出处】 | 剪辑要叠的链接卡或截图 | 【出处】{来源名称}，{日期}，{链接} |
| 【验收】 | 演示段到哪里看结果，观众能亲眼核对 | 【验收】看终端最后一行是 passed 还是 failed |
| `<!-- 待核 -->` | 录之前要核对的命令、按钮、数字、产品状态 | `<!-- 待核 录前确认按钮还叫这个名字 -->` |
| `<!-- 待录 -->` | 结果要等实际录完才能写 | `<!-- 待录 按实际跑出来的结果改口播 -->` |

备注一律独立成行，不混进口播句子里。标记后面直接写内容，不加冒号，跟情酱的标点规则一致，也方便检查脚本把它们和口播分开。

**备注要具体到能执行。** "画面切换""配一张图"等于没写。"切到官网定价页，从年付那一栏慢滚"才是剪辑能用的备注。

**画面来源优先用普通创作者能拿到的。** 录屏、截图、网页慢滚、终端、代码编辑器、文字卡、数据卡、真人出镜。真实人物、真实界面用真照片和真录屏，不用AI生图冒充。概念画面可以用AI生成，但要能看出是示意。

**别让一张静图停太久。** 一个画面超过十秒没有变化，观众的眼睛就没事干了。要么切下一张，要么在图上做标注、放大、划线。

### 轻量拍摄建议

默认只给这一块，让普通创作者一个人也能拍完。

- 拍摄形式，出镜口播、录屏、文字卡，或者混合
- 必备素材，录之前要准备好的截图、账号、测试数据、链接
- 最低剪辑成本，不做特效也能成片的做法
- 不建议做的复杂画面，比如需要动画师的流程动画

## 四、时长与字数

按情酱聊天的语速估算，约每分钟240字。语速快的作者可以按280字算，慢的按200字。制作备注、段落标题、发布包都不算口播字数。

| 时长 | 口播字数 | 至少要几件材料 |
|---|---|---|
| 3分钟 | 600到800 | 一件主材料，一个判断 |
| 5分钟 | 1000到1300 | 五件，不够就做到四分钟以内 |
| 8分钟 | 1700到2100 | 五件 |
| 10分钟 | 2200到2600 | 五到六件 |
| 15分钟 | 3200到3900 | 六件以上 |
| 20分钟 | 4300到5200 | 七件以上，考虑拆成两期 |

口播超过一千二百字，按材料关先数够五件，这条和文章一样。材料不够就把视频做短，三分钟讲透一件事比十分钟绕一件事强。

**宁短不长。** 超了先删背景铺垫，再删次要案例。关键结论和那个最具体的例子不能删，删了视频就只剩框架。

## 五、视频里的事实核验

视频比文章更难改错。文章发出去还能修改，视频发出去只能在评论区置顶勘误。所以核验放在录之前。

### 来源分三档

| 来源 | 能不能讲 | 怎么讲 |
|---|---|---|
| 官方公开资料，观众自己能打开 | 能 | 直接讲，【出处】给链接 |
| 非官方但有据，第三方实测、媒体报道、社区复现 | 能，但要屏上给证据 | 说清是谁测的，屏上放截图或链接卡 |
| 没有来源的推断和猜测 | 不能当事实讲 | 删掉，或者明说"这是我的猜测" |

同一件事有多个数字时，默认用官方数字，用户要求呈现争议时才并列。闭源产品、研究预览、内测功能，口播里说一句"这部分官方没公开，我不猜"。

发布日期、价格、开放范围这类事实，官方说了算。跑分、速度、效果这类数字是厂商自己测的，口播里说清"这是官方自己测的"，不跟第三方复现、自己的实验放进同一句。

### 事实核验清单

口播稿后面附一张表，每条硬事实一行，三档结论。

```
## 事实核验清单

| 事实点 | 来源 | 结论 |
|---|---|---|
| {产品}{日期}开放{功能} | 官方博客，{链接} | ✅ 直接讲 |
| 实测速度比上一版快 | {作者}的复现记录 | ⚠️ 讲的时候屏上放出处 |
| {公司}下个月会降价 | 我的推断 | ❌ 已删 |
```

### 亲历边界在视频里更容易破

脚本是录之前写的，录屏的结果还没发生。最常见的编造是预先写好演示结果，"跑完我发现它快得离谱"，"一次就成功了"。

用户没给实测记录时，演示段只写操作步骤和要看的点，结果写成 `<!-- 待录 -->`。录完把真实结果给回来，再写进口播。只有官方资料时，整期是资料解读，开头说清楚"我还没上手，先看官方怎么说"。

### 标题的边界

标题和封面可以有钩子，但只能写到事实允许的位置。钩子有点大的时候，口播前一两段就把边界补上，不等到最后。

## 六、完整分镜（用户要的时候再给）

默认不出完整分镜表，轻量拍摄建议够大多数情酱的视频用。用户要找剪辑外包、要用AI批量生成画面时再出。

```
| 镜头 | 对应口播 | 素材类型 | 画面说明 | 情绪 |
|---|---|---|---|---|
| 1 | {口播句} | 真人出镜 | 出镜，背景放产品首页 | 好奇 |
| 2 | {口播句} | 录屏 | 官网功能区慢滚 | 平稳 |
```

- **素材类型**用这几种，录屏或截图、真实人物照片、文字卡、数据图表、信息图、原文引用片段、概念画面、书籍封面、分屏、留白
- **镜头时长**一般三到五秒，开头和数据冲击处可以两三秒，故事展开和收尾可以五到八秒，单个镜头不超过十秒
- **不写时间码**。时间码按成片剪辑结果再标，脚本阶段估出来的只会变成噪音
- **情绪曲线**看四处，开头有好奇或紧张，中间有起伏，关键转折处有变化，结尾能收住。情绪要来自材料本身，不靠配乐硬推
- **覆盖检查**，每个人名、书名、数据都有对应画面，同一种素材不连排三个以上

## 七、B站发布包

| 项目 | 要求 |
|---|---|
| 标题 | 推荐一个，加两三个备选。四十字以内，手机列表里前二十字就要看懂 |
| 封面文案 | 八到十六个字，手机缩略图里能一眼认出主体和反差 |
| 简介 | 第一句说清这期讲什么，再两三句概述，参考链接一条一行。二百五十字以内 |
| 标签 | 六到十个，具体到产品名和话题，不堆泛词 |
| 置顶评论 | 一个情酱自己真想听大家回答的问题 |
| 出处列表 | 靠公开资料撑起来的事实型视频附上，个人经历和观点视频不附 |

- 标题同样不写翻案腔，"你以为的X可能完全是错的"这种模板是先立一个观众没有的误解再推翻它
- 章节时间戳等剪完按成片再加，脚本和发布包里都不预填
- 简介不复述口播，也不写"本期视频将为大家介绍"

## 八、文章改视频（模式F）

### 这是改编

不是逐字稿转录，念一遍公众号文章就是一期很难看完的视频。也不是借题重写，文章就是这期视频的全部素材，事实和判断一个都不新增。手里的材料已经够丰富，工作是语言转换和取舍，原文说得好的句子直接用，加上口播需要的过渡就行。

### 取舍

先定时长，按每分钟240字换算口播字数。五千字的文章做十分钟视频，口播只有两千四百字左右，大约留一半。

| 删 | 留 | 改成上屏 |
|---|---|---|
| 背景铺垫、次要案例、只为拔高的升维段、重复解释 | 主线判断、撑得住时长的那几件材料（超过一千二百字至少五件）、作者的犹豫和自我修正 | 数据表、长引文、截图、操作步骤里的命令 |

删的是枝，不是把每段都压缩一点。每段都压一点，得到的是一份更短的文章，不是视频。

取舍清单交给用户，原文哪几段保留、删去、改成上屏，各一句理由。用户看一眼就知道哪段被拿掉了，觉得不该删的可以要回来。

### 重排

- **开头前置**。文章可以用三段慢慢铺场景，视频不行。最能留人的事实在原文第五段，就把它提到前30秒。判断本身不改，只改出场顺序
- **图片位置变画面**。原文标"图片"的地方，正好是【屏幕】备注的位置
- **长引文全文上屏，嘴上念一句**。念的那句仍是原话，不能改写后当原话念
- **回环呼应看距离**。文章里开头埋、结尾响，隔着五千字没问题，视频里隔十几分钟观众已经忘了。挪近，或者拿掉
- **小标题变段落标题**。模式A的文章本来不加小标题，改成视频时要补上描述性的段落标题，给录制者看

### 要换掉的东西

| 文章里 | 视频里 |
|---|---|
| 公众号固定尾部，点赞在看星标、作者署名、投稿邮箱 | B站固定尾部 |
| 如下图、上文、文末、往下翻、点击阅读原文 | 你看画面上、刚才说到、最后、简介里有链接 |
| 文章开头没有自我介绍 | 前两三句补上"大家好，我是情酱" |
| 读者 | 你，或者屏幕前的你 |

### 时效

文章写完以后，产品状态、价格、版本号、排行榜都可能变了。改编时不悄悄更新成新数字，在那句后面标 `<!-- 待核 原文写于{日期}，录前确认现在的状态 -->`。用户确认了再改口播，改了以后事实核验清单里同步。

### 不是情酱写的文章

用户拿来的文章作者不是情酱时，原文的"我"在视频里要变成"作者说他"。别人的经历不能念成情酱的经历，这一条比任何节奏都重要。口播开头说明这期在聊谁的哪篇文章，转述别人的文章之前先提醒用户确认使用权。

### 改编核对

交付前逐条对照原文。

- 每个事实能在原文找到对应段落
- 数字、名称、版本、引语原文没有漂移
- 情态和判断强度一致，"可能"没有变成"肯定"，"我还拿不准"没有被删掉
- 原文是资料解读，视频没有升级成亲测
- 原文里有无源论断时，按情酱创作模式处理，能查到就补出处，查不到就不念，或者明说没找到出处

## 九、没有收的写法

参考仓库和那四位UP的有些做法，在它们自己的账号里成立，跟情酱的禁区冲突，这里没有收。

| 参考写法 | 为什么不收 |
|---|---|
| 编一个场景开场，"凌晨两点，小李还在加班" | 假细节。情酱的开头必须是素材里真有的事 |
| 第一人称引入别人，"我有个朋友" | 没有这个朋友就是编造亲历 |
| 口语连接词"说白了""这对你意味着什么""但实际上" | 情酱的高频AI味禁词和翻案腔外衣 |
| 反常识标题模板"你以为的X可能完全是错的" | 翻案腔，先立误解再推翻 |
| 结尾"第一第二第三"复盘全片 | 套话结构，收尾回扣开头那件事就够了 |
| 每段固定"破"一下再"立"一下 | 情酱收了其中有用的部分，指出问题后紧跟办法，不连续两段只吐槽。但不为了凑结构硬造一个"破" |

## 十一、讲解骨架（概念、机制、工具、成品）

情酱的五种文章原型决定拍法。下面四套骨架决定**正文怎么往前走**，跟原型大致对应，不是一一对应。写脚本前按这期要讲清的东西先选一套，不要中途换。

四位相近定位的技术口播里，下面这几条工作习惯可以直接复用。口气和人设不搬。

### 四条共用

1. **先讲卡在哪，再给名字。** 术语是后来贴上去的标签。先说输入是什么、中间发生了什么、输出长什么样，再告诉观众这个过程现在叫什么
2. **一个贯穿案例走完全程。** 不要每个术语换一个新故事。同一条任务从错误答案走到能用的答案，观众才跟得上
3. **归因拆开。** 模型、框架、工具、脚本、提示词、人，各自贡献分开说。换模型结果变了，先看提示词和工具有没有一起变。观测到的现象不要直接当成原因
4. **演示有验收点。** 每一步写清预期、动作、到哪里去看结果。工具自己报完成了，还要打开文件、日志或页面看一眼。假数据、手工模拟、省略的步骤、缩小的规模，口播里标出来。跑通一次不等于能上生产

来源分层跟第五节同一套三档，效果类的说法再细一点，分成已复现、作者自己的实验、厂商自报、猜测。这四类不能混在一句里当同一级事实。

### 按原型选骨架

**概念解释**（现象解读型、方法论型里讲清楚一个词时用）

```
一句人话定义
  ↓
最小实例，能上屏
  ↓
它实际怎么走，输入、过程、输出
  ↓
大家容易卡在哪，必须是真会混的点，不是先立误解再推翻
  ↓
边界、来源、仍然有用的部分
```

**问题链**（机制课、Agent、协议、底层原理）

```
一个具体任务
  ↓
最容易想到的办法
  ↓
它哪里不够
  ↓
只加一个机制，仍用刚才那个任务再走一遍
  ↓
这才给这个机制起名字，同时讲限制
  ↓
收回开头那个任务，留一个观众能自己验证的下一步
```

入门系列同一套循环。每次只加为解决新问题所需的那一个组件，加完回到总图。没讲完的部分不能装成已经掌握。

**工具课**（产品体验型、工具分享型）

```
这期要做成哪一件具体的事
  ↓
配置到能第一次跑通
  ↓
新需求带出下一个功能，不要功能清单
  ↓
到文件、日志或页面验收
  ↓
失败就排查，不跳过
  ↓
适用条件和硬约束
```

**成品先亮**（调查实验型、可展示结果的教程）

```
先让观众看见成品或问题场景
  ↓
最小实现思路
  ↓
按步骤做，一次只改一个参数，看画面怎么变
  ↓
失败、成本和做不到的地方照说
  ↓
可复用的步骤或工程入口，邀请去试，不要把能运行说成已经好看
```

**比较课**不要写成站队。先定比较口径，两边机制都讲，优点和失效条件一起给，结论写成"在这些条件下我会选谁"。个人预测不写成事实。模型和评测对齐提示词、工具、采样和评价方法再比。

### 开头怎么接

情酱的四种开头仍然先选。骨架只决定开头之后怎么走。

- 问题链、概念解释，钩子用一个能验证的问题或观众刚见过的热词
- 工具课，钩子用这期要做成的那件事
- 成品先亮，钩子用成品或现场痛点

不要为了像某位UP，改成"那么问题来了"或"你以为的X"。

### 画面怎么配

- 角色、模块在画面上的位置和颜色保持稳定。放大局部之后要回到总图
- 嘴上讲因果，屏上放结构、状态或对照。一次不要让所有元素一起变
- 操作段只放能验证结论的界面或输出，不放气氛空镜
- 动画用在机制说不清的地方，简单工具能说清就不要做动画
- 每个画面只解释当前这一步

### 标题

标题写具体问题、学习结果或实测成本，不单列工具名。可以有追问，强度不能超过正文证据。四十字以内、前二十字能看懂，这条不变。

### 写进脚本的验收位

工具课和成品先亮的脚本里，演示段除了 `【屏幕】` 和 `<!-- 待录 -->`，再加一行观众能看见的验收。

```
【屏幕】终端跑完测试的输出
【验收】看最后一行是 passed 还是 failed，失败就把报错叠上屏
<!-- 待录 按实际结果改口播 -->
```

没跑过的步骤写演示计划，不写"我发现它一次就过了"。
